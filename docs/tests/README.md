# 自动化测试

这些脚本用于**在没有 ROS 2 环境的情况下**验证工程代码的正确性。
原理是把 `rclpy`、`launch` 等 ROS 2 模块用轻量桩（stub）替换掉，
然后真实执行我们的代码，检查行为是否符合预期。

## 为什么值得做

工程的评分项里有"**方案可行性与工程落地 15 分**"。
能拿出可复现的自动化测试，说明代码不是"跑一次碰巧成功"，
而是**行为可验证、改动可回归**的。测试本身也是防回归的保障：
后续修改调参时，跑一遍就知道有没有把原有逻辑改坏。

## 运行方式

不需要安装 ROS 2，只要有 Python 3 即可：

```bash
cd <工作区根目录>

# 巡检调度节点的业务逻辑（7 项）
python3 docs/tests/test_patrol_node.py

# 四个 launch 文件的加载与容错逻辑（13 项）
python3 docs/tests/test_launch_files.py

# Keepout 掩膜生成器（9 项）
python3 docs/tests/test_keepout_mask.py

# SLAM 管线诊断脚本（12 项）
python3 docs/tests/test_diagnose_slam.py

# 工程静态检查（语法 / XML / YAML / 使用顺序）
python3 docs/tests/test_static_checks.py

# Nav2 参数版本适配检查
python3 docs/tests/test_nav2_params.py

# 文档内部链接与路径检查
python3 docs/tests/test_doc_links.py
```

脚本会自动创建临时目录存放桩模块，结束后自动清理。
全部通过时退出码为 0，有失败时退出码为 1。

## 覆盖范围

### `test_patrol_node.py` —— `community_patrol/patrol_node.py`

| # | 测试项 | 验证内容 |
|---|---|---|
| 1 | 正常流程 | 站点按顺序执行、导航目标发送次数正确 |
| 2 | 失败后重试 | 单站导航失败会重试，重试成功则继续 |
| 3 | 跳过逻辑 | 重试次数用尽后跳过该站，**整体流程不中断** |
| 4 | 红绿灯等待 | 红灯期间等待，状态变绿后放行 |
| 5 | 红绿灯超时 | 长时间红灯不会卡死，超时后按既定策略继续 |
| 6 | 识别超时 | 视觉组未返回结果时不会阻塞，触发消息格式正确 |
| 7 | 配置校验 | 站点表缺少坐标时能报出可识别的错误 |

**这些测试实际发现并修复了两个问题：**
1. `_load_waypoints` 重复调用会把站点追加成两份（同一站点跑两次）
2. 节点初始化失败时会抛出完整 traceback，现场排查困难——已改为打印可照做的提示

### `test_launch_files.py` —— `community_nav/launch/` 下全部三个启动文件

| # | 测试项 | 验证内容 |
|---|---|---|
| 1 | `sim.launch.py` 生成 | 6 个参数声明 + 3 个子启动 + 1 个 spawn 节点 |
| 2 | `mapping.launch.py` 生成 | 4 个参数声明 + 2 个节点（slam_toolbox / lifecycle_manager） |
| 3 | `navigation.launch.py` 生成 | 5 个参数声明 + 2 个子启动 + 1 个巡检节点 |
| 4 | sim 缺模型文件 | 报错信息列出**可用型号**和 `TURTLEBOT3_MODEL` 的当前值 |
| 5 | **sim 的 spawn 参数** | 自己生成机器人时，`-file` 后面**必须是非空路径** |
| 6 | mapping 节点配置 | 确认启动的是 `async_slam_toolbox_node` + 生命周期管理，且 `node_names` 正确 |
| 7 | mapping 缺包 | 报错信息里带上**对应的 apt 包名**，可以直接复制执行 |
| 7b | **mapping 缺 SLAM 参数文件** | **启动瞬间就报错**，并提示重新 `colcon build` |
| 7c | **mapping 的 RViz 设了 `on_exit`** | 防止 RViz 崩溃时把整个 launch 带崩（见下） |
| 8 | navigation 内容 | 确实包含了 Nav2 bringup、RViz 和巡检节点 |
| 9 | navigation 传参完整 | `map` / `use_sim_time` / `params_file` / `autostart` / `use_composition` 一个不少 |

**测试 7c 对应一个真实踩到的坑：**

> `mapping.launch.py` 原来用 `IncludeLaunchDescription` 引入
> `nav2_bringup/rviz_launch.py`。而 **RViz 在 WSL 下会因为图形问题崩掉**——
> 它一崩，**整个 launch 会被触发关闭，`slam_toolbox` 被一起带走**，
> 于是 `/map` 永远出不来。
>
> 日志里的顺序正是这样：`rviz2` 先报 `GLSL link result` 死亡，
> 紧接着 `lifecycle_manager` 就走 SIGINT → SIGTERM → SIGKILL 的关闭流程。
>
> **修法：改成直接起 `rviz2` 节点，并给它设 `on_exit` 只打一条日志。**
> 这样 **RViz 挂了建图照样继续，地图还能建出来**。
>
> 教训：**可视化工具不该拥有"杀死主流程"的权力。**

**这组测试在真机联调中抓出了一个真实故障：**

> TurtleBot3 官方的 `spawn_turtlebot3.launch.py` 会把 `-file` 参数传成**空字符串**，
> 导致 `spawn_entity.py` 报
> `UnboundLocalError: local variable 'entity_xml' referenced before assignment` 并退出。
>
> **后果：机器人在 Gazebo 里根本没生成**，`/scan` 和 `/odom` 话题完全不存在，
> 表现为"Gazebo 启动了但什么都收不到"——这个现象**非常容易误判成插件问题或网络问题**。
>
> **修法：`sim.launch.py` 不再调用官方的 spawn 启动文件，
> 改为自己拼 `spawn_entity.py` 的参数**，模型路径在 launch 文件里显式计算，
> 并且路径不存在时直接列出可用型号。
>
> 教训：**依赖第三方启动文件的内部参数传递是有风险的**，
> 关键路径上宁可自己显式控制。

**这组测试的价值：** 它等价于 `ros2 launch --show-args` 的效果，
但**不需要 ROS 环境就能跑**。任何 launch 文件的语法错误、导入错误、
依赖查找失败，都会在几秒内暴露，而不是等到启动 Gazebo 时才发现。

## 说明

- 桩模块只实现被调用到的那部分接口，**不能替代真实 ROS 2 环境下的集成测试**。
  仿真环境搭好后，仍需按 `docs/01-环境搭建指南.md` 的验收标准做真机验证。
- 想要扩展测试，直接在对应文件里追加 `try/except` 块并调用 `record()` 即可。

这类"静默失效"最危险，只有测试能抓到。

### `test_diagnose_slam.py` —— `docs/scripts/diagnose_slam.py`

| # | 测试项 | 验证内容 |
|---|---|---|
| 1 | 激光读数在变 | 判定为"机器人确实在移动" → 问题在 RViz 显示 |
| 2 | 里程计在变但激光不变 | 判定为"**卡住空转**" → 出生点或物理问题 |
| 3 | 完全收不到激光 | 判定为"仿真没起来" |
| 4 | 两者都不动 | 判定为"没按遥控键 / 卡住" |
| 5 | 快照完整性 | 五个环节 + 指纹 + 地图栅格全部输出 |
| 6 | 指纹算法 | 正确忽略 `inf` 和过小的距离值 |
| 7 | `--spin` | 注册定时器并发出指定角速度的旋转指令 |
| 8 | 结束时停车 | 诊断跑完会发一条零速指令，不会让机器人一直转 |
| 9 | `--spin 0` | 不自动控制，改为人工遥控 |
| 10 | **激光在变但 `/map` 没发布** | 判定为"**SLAM 没工作**"，**不误判成 RViz 显示问题** |
| 11 | 地图累计计数不被重置 | 前几轮收到过地图，就不该再判"SLAM 没工作" |
| 12 | **`/map` 用默认 QoS** | 防止 QoS 不兼容造成假阴性（见下） |

**测试 12 修掉了一个更隐蔽的 bug —— 诊断工具自己产生的假阴性：**

> 脚本最初给 `/map` 的订阅指定了 `TRANSIENT_LOCAL` 持久性。
> 而 ROS 2 的 QoS 兼容规则是：
>
> | 订阅者 | 能收哪些发布者 |
> |---|---|
> | **VOLATILE**（默认） | VOLATILE ✅ 和 TRANSIENT_LOCAL ✅ |
> | **TRANSIENT_LOCAL** | 只有 TRANSIENT_LOCAL ✅；发布者是 VOLATILE 时**一条都收不到** ❌ |
>
> `slam_toolbox` 发布 `/map` 用的是 VOLATILE。
> 于是**明明 SLAM 正常，诊断脚本却一条地图都收不到**，
> 报告成"SLAM 没工作"——**把人引向了完全错误的方向**。
>
> **教训：诊断工具应该用最宽松的 QoS。**
> 它的职责是"看到真相"，而不是"按理想配置去挑剔"。
> 收不到数据时，先怀疑自己，再怀疑被测对象。

**测试 10 修掉了一个会导致误判的漏洞：**

> 原来的判定顺序是先看"机器人动没动"。于是当**机器人正常移动、激光也在变**，
> 但 **SLAM 压根没发地图**时，脚本会得出
> "问题在 RViz 显示"——**这个结论是错的**，会把人引到完全错误的方向。
>
> 修法：把"地图一条都没收到"提到前面单独判定，
> 并给出针对 slam_toolbox 生命周期状态的排查步骤。
>
> **教训：诊断工具的判断顺序本身就是设计的一部分，
> 顺序错了，结论比没有结论更糟。**

**为什么要有这个诊断脚本：**

排查"车不动 / 地图不长 / RViz 没反应"这类问题，逐条敲命令既慢又容易问错方向。
这个脚本同时盯住整条链路的五个环节，并在结束时给出**明确结论**：

```
Gazebo 时钟 /clock → 激光 /scan → 里程计 /odom → 控制 /cmd_vel → 地图 /map
```

**它基于一个关键的物理事实：**

> Gazebo 的 `/odom` 是**开环**的——由轮速积分得来，**不测量实际位移**。
> 所以"轮子在转、`/odom` 在变"**不能证明机器人真的动了**。
> 真正能证明移动的是**激光读数发生改变**。

正因为同时记录这两者，脚本才能区分"真的在动"和"卡住空转"这两种
**外部表现几乎一样、但处理办法完全不同**的情况。

### `test_static_checks.py` —— 全工程静态检查

| 检查项 | 说明 |
|---|---|
| Python 语法 | 所有 `.py`，编译一遍 |
| XML 格式 | `package.xml` |
| YAML 解析 | 所有配置文件 |
| ★ **"函数内先用后定义"** | 语法检查查不出、只有运行才炸的那一类错误 |

**为什么要有第 4 项：**

开发中真实踩到过——launch 文件里把
`from launch.conditions import IfCondition`
写在了使用 `IfCondition` 的那一行**之后**，运行时直接抛 `NameError`。
编译能过、语法检查能过，**只有真跑才炸**。

本脚本用 AST 分析把它提前抓出来，并且**自带一个自测**：
故意喂一段写错的代码，确认检查器能抓到——**防止它退化成"永远通过"的摆设**。

> 实现上有个容易误判的地方：Python 的 `ast.walk` 是**广度优先**，
> 遍历顺序不等于行号顺序。判断"是否在使用前定义"时必须取该名字
> 所有绑定位置中**最小的行号**，否则会误报（这个坑也踩过）。

### `test_nav2_params.py` —— Nav2 参数版本适配检查

以 **Nav2 Humble 官方发布包里的 `nav2_params.yaml` 为基准**做三项检查：

| # | 检查 | 说明 |
|---|---|---|
| 1 | 顶层键是否齐全 | 与官方 15 个顶层键比对 |
| 2 | **有没有混入新版专有参数** | 见下 |
| 3 | 关键参数值抽查 | 18 项，每项带"为什么这么设"的说明 |

**检查 2 是最重要的。** Nav2 参数在不同大版本之间有**实质性差异**：

| 参数 | Humble | Jazzy 及之后 |
|---|---|---|
| 行为树节点库 | **必须**在 `plugin_lib_names` 显式列出 | 自动加载默认集合，**再列出会重复注册直接失败** |
| 代价地图话题 | `costmap_topic` / `footprint_topic` | `local_costmap_topic` / `global_costmap_topic` |

**在 Humble 上写新版本的参数名不会报错，只会静默失效**——
恢复行为拿不到代价地图数据，车卡住时无法脱困。这类问题最难排查。

**这个检查工具在开发中抓出过两个真实错误**（就是把上面两行写错了）。

### `test_doc_links.py` —— 文档内部链接与路径检查

| 检查对象 | 说明 |
|---|---|
| Markdown 链接 | `[文字](目标)` 和图片 `![说明](目标)` |
| **反引号里的路径** | 例如 `` `docs/scripts/diagnose_slam.py` `` —— 不会渲染成链接，但写错了同样让人找不到文件 |

跳过外链（http/https）和纯锚点。目标路径**相对于所在文件**或**相对于工作区根目录**两种写法都支持
（本项目历史文档两种写法都有）。

**为什么需要它：** 文档本身就是评分项（"文档质量 5 分""排版与规范 5 分"）。
一条指向不存在文件的链接，评审点进去就是死路——内容写得再好，第一印象也会打折。
十几份文档、几十条引用，人工核对很容易漏。

**这个检查抓出过一个真实问题：**

> `07-给仿真组的对接说明.md` 里把 17 张截图的文件名写成了
> `9.24智慧社区培训_p10~p26_gazebo.png` ——
> 那是个**页码范围**，不是一个真实文件名。
> 仿真组照着找会找不到文件。
>
> 已改成准确写法：说明文件名的**实际规律**并列出关键几张的用途。
